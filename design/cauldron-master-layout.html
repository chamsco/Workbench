Verdict

About 15% of the change fits; the sync part is the other 85% of the effort

By your 20% rule: authors, members, owners and reply threads are small and also useful with one person (a thread you opened from a message, an agent as an author). Real-time sharing between machines is not small, and it is the part that decides everything else. I would build the first part now and keep the second as its own decision.

The flaw to avoid, from your own screenshot. The first Amp user says he never knows whether his next message goes to the agent or is plain chat, and that an @ mention turns it into chat. A shared thread has to answer that on the composer. Screen 1 has a Send-to switch: Coordinator or Team. Team messages never wake an agent. The coordinator reads them only when you address it with the switch or quote one.

Rules for a multiplayer project

  • Every agent runs on its owner's machine with its owner's logins. Workbench never holds credentials, so a member cannot spend another member's subscription.
  • The project owner approves merges and global memory. Members propose.
  • Project memory is shared only for pinned notes (D4). Personal memory is never shared.
  • Cost is shown per person.

Decision D5, how two machines share a Space. (1) A hosted relay: fast to build, but it breaks the no-hosted-backend rule in the plan. (2) Git: a Code project already keeps requests and handoffs in .backspace/ in the repo, so the state shares through the repo for free, but it is not live. (3) A small relay for live chat only, later. My recommendation is (2) for state now and (3) when a second person exists. One question decides it: who is the second person, and are they working in the same repo? If it is a collaborator in the same repo, (2) is enough. If it is someone without a repo, that needs (1) or (3).
