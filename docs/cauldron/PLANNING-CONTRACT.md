# Planning contract (M4 → M5)

What the planning stage hands on, and what M5's Builder and Rampart will read. Written at the M4 closure, 14 Nov 2026.

## The canonical spec

The canonical spec for a long task is **`.backspace/planning/spec.md`** (in code, `planning::SPEC`). It is the only spec M5 consumes. It is generated by code from the typed checklist (`submit_spec`), never written by a model. It is valid only while both of these hold:

- its SHA-256 equals `ProjectState.planning.spec_sha256` (the file that was put to the user);
- that hash equals `ProjectState.planning.approved_sha256` (the file the user said yes to).

A spec.md whose hash differs from `approved_sha256` is not approved. A consumer must check the hash against `approved_sha256` before reading the file, not just whether the file exists. `planning::ticket_refusal` is the reference check.

## What comes with it

- `.backspace/planning/baseline.json`: the record of the last capture. It holds the task type, whether the baseline held, every command run (exit code, ms, the end of its output) and the screenshots.
- `.backspace/planning/baseline/`: copies of the baseline screenshots, named in baseline.json with their SHA-256. The live files will change, so these copies are the "before".
- spec.md itself carries:
  - the goal;
  - the acceptance criteria, numbered A1… under `## Acceptance` (the numbering `spec::coverage` reads);
  - a criterion → test table;
  - the non-goals, constraints and dependencies;
  - the baseline summary;
  - the checklist.

Under §7.1, Rampart is meant to see spec.md and the baseline, and Builder is meant to see the sealed tests. That split is M5's to enforce, and nothing enforces it yet.

## What is not an input

Plan mode's root `SPEC.md` (spec.rs, written from a Code-chat Plan reply) is **not an input to M5**. It is a separate interview document with its own rules gate and its own coverage gate on tickets. It is kept as it was, and M5 must not read it as the long path's spec. Merging the two is a later decision.

`tests.md` is not produced at M4. Rampart writes the tests in M5.

## Commands before approval

No baseline command runs before the user has approved that exact list. A submission whose other items pass puts the commands to the user (`planning::commands`, bound to `commands_sha256`). After a plain yes, the next submission with the same list runs them. A changed command is a new list and needs a new yes.

## Intake default

Intake stays **off by default** (`[intake] enabled = false`) until the §10 router evaluation has run and been reviewed. With intake off, no task reaches the long path through triage, so the planning stage does not run. The planner works as it did before M4 (tested in `planning.rs` and `intake.rs`). The default is not changed by M4.
