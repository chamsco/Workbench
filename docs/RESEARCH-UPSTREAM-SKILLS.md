into this checkout (`C:\Users\chamy\Documents\code\Workbench`, `chamsco/Workbench`), and

## (a) Per-repo summary

### A. `DietrichGebert/ponytail` — a skills collection **plus** a multi-agent plugin

**What it is:** an agent-behaviour pack ("the laziest senior dev in the room": make the
smallest complete change). It is a **Claude-Skills-style collection at its core** — six
folders under `skills/`, each with a `SKILL.md` and nothing else — wrapped in a
distributable **plugin** for ~20 harnesses. Both readings are true; the `skills/`
directory is what matters to Backspace.

**The six skills** live in `skills/<name>/SKILL.md`. Each is a single file with **no
sibling files**. `skills/plugin.json` (167 B) declares `"skills": "."`, i.e. the folder
itself is the skill root:

```json

  "name": "ponytail",
  "description": "Lazy senior dev mode. Forces the simplest solution that works: YAGNI, stdlib first, one line over fifty.",
  "skills": "."
}
```

**Everything else in the repo is adapter/packaging, not skills.** From the recursive
tree: `commands/*.toml` (6 CLI command defs), `.opencode/command/*.md` (6),
`.opencode/plugins/*` (`index.js`, `ponytail-frontmatter.cjs`, `ponytail.mjs`),
`hooks/` (a Claude Code statusline "band": `band/*.ts,tsx`, 8 JS lifecycle hooks,
`ponytail-statusline.{sh,ps1}`, 5 `*-hooks.json`), `scripts/` (5 JS: build/publish
OpenClaw skills, check rule copies, check versions, cursor hooks, uninstall), `tests/`
(~20 files), `assets/` (screenshots/logos, ~5 MB), `benchmarks/`, `docs/`, `examples/`
(11 end-user examples), `i18n/` (4 translated READMEs), and a manifest per host
(`.claude-plugin/`, `.codex-plugin/`, `.kimi-plugin/`, `.qoder-plugin/`,
`.devin-plugin/`, `.grok-plugin/`, `.kiro/`, `.cursor/`, `.clinerules/`, `.windsurf/`,
`.agents/`, `.qoder/`, `plugin.json`, `plugin.yaml`, `gemini-extension.json`,

stray `__init__.py` (8936 B). The six skills are **duplicated** under `.openclaw/skills/`
with slightly different sizes, generated by `scripts/build-openclaw-skills.js`.

**Install instructions (README "Install" + `INSTALL.md`, 15774 B):**

- Claude Code, as a plugin: `/plugin marketplace add DietrichGebert/ponytail` then
  `/plugin install ponytail@ponytail`.
- Codex: `codex plugin marketplace add DietrichGebert/ponytail` then
  `codex plugin add ponytail@ponytail`, then trust the two lifecycle hooks.
- **Any other agent:** "copy `AGENTS.md` into your project, or ask your agent to install

- Security note from the README: "Only install ponytail from `DietrichGebert/ponytail` on
  GitHub or `@dietrichgebert/ponytail` on npm. It never ships `.exe` or `.dll` files; a
  copy that does is not mine."

**Relevance to Backspace:** `ponytail` itself is already vendored here (see (c)). The
other five are the new material, and they are *commands* upstream — `/ponytail-review`,
`/ponytail-audit`, `/ponytail-debt`, `/ponytail-gain`, `/ponytail-help`.

## How the loader actually works (the constraints the plan must satisfy)

Everything below is from `crates/core/src/skills.rs` (318 lines) and its callers.

**Discovery — `Skills::load(&workspace)` (`skills.rs:137`)**, in load order, later winning:

1. `DEFAULTS` (`skills.rs:25`), built by the `vendored!` macro (`skills.rs:11`) from
   `include_str!("../skills/<skill>/<file>")` — compile-time embedding, no network.
2. `user_dir()` (`skills.rs:20`) = `$HOME` or `$USERPROFILE` + `.config/backspace/skills`.
3. `<workspace>/.backspace/skills` (`skills.rs:150`).

A directory qualifies only if `<dir>/<name>/SKILL.md` is a file (`skills.rs:157`), and the
folder's name becomes the skill name. For folder-based skills the code then loads **only
files directly inside that folder whose extension is exactly `md`** (`skills.rs:160-169`,
a non-recursive `read_dir`). Consequences: satellite files must sit **beside** `SKILL.md`
at the top level (they do, in both repos); subdirectories such as the `reference/*.md`
example in `docs/SKILLS.md:52` are **not** recursed into; non-`.md` assets are ignored; and
a `.MD` extension would not match.

**Description — `fn skill()` (`skills.rs:207-222`)** is a deliberately naive YAML read:
strip a leading `---`, take text up to the first `\n---`, then find the first line that
literally *starts with* `description:` and return `rest.trim().trim_matches('"')`. Any
other frontmatter key is ignored. There is no YAML parser, so `>`/`|` block scalars are
not expanded, and a description continued on the next line is lost.

**Loading a skill — `Skills::read(name, file)` (`skills.rs:186`)** defaults `file` to
`SKILL.md`, and when the skill has other files it appends
`(Other files in this skill, readable with `file`: …)`. The `skill` tool
(`harness.rs:2228-2234`, definition at `harness.rs:3352`) is how an agent reads either the
body or a satellite file by bare filename.

**Index and injection.** `Skills::index()` (`skills.rs:178`) renders one line per skill as
`- {name}: {description}`, embedded in the system prompt at `harness.rs:984-999` together
with `ADAPTER` and the bodies of whichever skills the role injects
(`config.rs:135-147`: `main_skills` defaults `grilling`, `to-tickets`; `worker_skills`
defaults `ponytail`; `triage_skills` defaults `triage`). `Skills::load` is called once when
the harness is built (`harness.rs:425`), so new skills appear in the *next* session; the
Settings panel re-reads on every call (`skills_catalog`, `crates/tauri-app/src/main.rs:856`).

**The two user-facing drop-in locations**, exactly:

1. `~/.config/backspace/skills/<name>/SKILL.md` — on this machine
   `C:\Users\chamy\.config\backspace\skills\<name>\SKILL.md`. Shown in Settings as "Yours".
2. `<project>/.backspace/skills/<name>/SKILL.md` — on this machine
   `C:\Users\chamy\Documents\code\Workbench\.backspace\skills\<name>\SKILL.md`. Shown as
   "This project", and it wins over both the vendored copy and the user folder. Named
   "this project" because `.backspace/` ignores itself in git (see *Where your files
   live* in the README).

A folder whose name matches a built-in **replaces** it rather than sitting beside it
(`docs/SKILLS.md:17-20`, asserted by the test at `skills.rs:270-300`).

**The adapter note file(s).** There is **no separate adapter file** — the note is the
single `pub const ADAPTER` string at `crates/core/src/skills.rs:38`, appended to the system
prompt at `harness.rs:984`. It is documented in `docs/SKILLS.md` and in the Skills section
of the README, and grepping every `.md` in the repo for `ADAPTER`/`adapter` turns up
only those places (plus one unrelated prose use inside `tdd/SKILL.md`). So "edit the
adapter note" means editing that one constant.

Related supporting files, for reference: `crates/core/src/config.rs:135-147` (injection
lists), `crates/tauri-app/src/main.rs:850-917` (`skills_catalog`, the UI template, the
dirs it reports), tests at `skills.rs:224-317` and `crates/core/tests/e2e.rs:239`, and the
design note at `docs/SKILLS.md` — including its observation that a repo-side *library* of
installable-but-unshipped skills "would be the next step" (`docs/SKILLS.md:71-74`), which
is not implemented today.

## (d) Compatibility, then the install plan

### Compatibility verdict

**Layout: compatible, exactly.** Both repos put `<name>/SKILL.md` one level under a
`skills/` directory, with satellite `.md` files beside it as bare-filename links such as
`[RECIPES.md](RECIPES.md)` — which is precisely what `Skills::load` scans. No subdirectory
or non-`.md` dependency exists in either repo, so the loader's non-recursive `.md`-only
scan loses nothing.

**Frontmatter: compatible for emil (15/15), broken for ponytail as shipped (0/6).** I
re-implemented `fn skill()`'s parse byte-for-byte and ran it over all 21 upstream
`SKILL.md` files plus the 7 local ones:

- All 15 emil skills parse to a correct, full one-line description (`---` at byte 0, no
  BOM, LF endings, `name:` + `description:` each on one line, no continuation lines).
  Em dashes, quotes and parentheses inside descriptions are harmless.
- **All six ponytail skills parse to the single character `>`.** Upstream writes the
  description as a YAML folded block scalar:
  ```yaml
  description: >
    Lazy senior dev mode: the smallest change that fully solves the task, and a
    reply a busy human understands in one read. …
  ```
  The naive reader takes the text after `description:` on that line, which is `>`. The
  subsequent indented lines are dropped.
- **This is a live bug in the current checkout, not just a future risk:** the vendored
  `crates/core/skills/ponytail/SKILL.md` has the same folded form, so today the Settings
  list shows ponytail's description as `>` and the system-prompt index renders
  `- ponytail: >`. The existing test misses it because
  `defaults_load_with_descriptions` (`skills.rs:229`) only asserts the description is
  non-empty, and `">"` is non-empty.
- Every file is BOM-free and LF-only, and `---` is the literal first three bytes, so the
  `strip_prefix("---")` guard holds everywhere.

**Extra frontmatter keys: ignored, with one semantic mismatch.** Three emil skills set
`disable-model-invocation: true` — `pick-ui-library`, `prototype`, `review-animations` —
and their descriptions say so explicitly ("Only runs when explicitly invoked; it does not
trigger on its own"). Backspace has no such concept: every loaded skill appears in the
index and can be injected, so these three would become model-invocable. The parser ignores
the unknown key without error, so this is behavioural, not a parse failure. `ponytail` also
carries `argument-hint` and `license: MIT`; both are ignored harmlessly.

**Vocabulary: needs adapter coverage.** Neither repo mentions "Skill tool", `TodoWrite`,
`Task tool`, `Write/Read/Bash tool`, or `skills.sh` in its skill bodies (counts: 0 across
all 21 files), so no tool-name translation is needed for them. What is present:
`/ponytail*` slash commands (27 occurrences across the ponytail skills, 4 mentions of
"Claude Code"), and in emil `subagent` (4 occurrences, notably
`improve-animations`'s "fan out read-only subagents… an executor subagent… in an isolated
worktree") and the sibling-file references. The existing `ADAPTER` already maps the
ponytail slash commands — but it names only `review`, `audit`, `debt` and `gain`, and not
`/ponytail-help`, which would be new. Nothing in `ADAPTER` yet tells the agent that a
skill's satellite files are reachable with the `skill` tool's `file` argument.

**Context weight.** `write-swift` is a single 42 KB body with no satellite files, so
`skill write-swift` puts all of it in context at once; `emil-design-eng` (27 KB) and
`apple-design` (23 KB) are next. Since injection is opt-in per role and the index carries
only one line per skill, adding all 20 costs the system prompt roughly 20 lines until
something is read or injected.

### Install plan

Two routes. Route 1 needs no rebuild and is the right way to try these; Route 2 makes them
ship with the app on every install. Both are additive — nothing existing is overwritten
because none of the 20 names collides with the 7 vendored names.

#### Route 1 — drop-in (no rebuild, reversible)

1. Get the sources (verbatim copies; do not hand-edit bodies):

   ```powershell
   $s = "$env:TEMP\skills-src"; New-Item -ItemType Directory -Force $s | Out-Null
   git clone --depth 1 https://github.com/emilkowalski/skills "$s\emil"
   git clone --depth 1 https://github.com/DietrichGebert/ponytail "$s\ponytail"
   ```

2. Choose the target. For **just this project** use
   `C:\Users\chamy\Documents\code\Workbench\.backspace\skills\`; for **every project on
   this machine** use `C:\Users\chamy\.config\backspace\skills\`. Both are read by
   `Skills::load`; the project one wins on a name clash.

   ```powershell
   $dst = "$env:USERPROFILE\.config\backspace\skills"          # "Yours"
   # $dst = "C:\Users\chamy\Documents\code\Workbench\.backspace\skills"   # "This project"
   New-Item -ItemType Directory -Force $dst | Out-Null
   ```

3. Copy the 15 emil skills, folders and satellite files together:

   ```powershell
   Copy-Item -Recurse -Force "$s\emil\skills\*" $dst
   ```

   That yields `$dst\animate\{SKILL.md,RECIPES.md}`, `$dst\emil-design-eng\SKILL.md`,
   `$dst\improve-animations\{SKILL.md,AUDIT.md,PLAN-TEMPLATE.md}`, and so on for all 15.
   Do **not** copy `performance-cheatsheet.md` into a skill folder — if it were placed
   inside one it would be listed as that skill's satellite file; it belongs nowhere in
   particular.

4. Copy the 5 *new* ponytail skills (skip `ponytail` itself, which is already vendored);
   each is one file:

   ```powershell
   foreach ($n in 'ponytail-review','ponytail-audit','ponytail-debt','ponytail-gain','ponytail-help') {
     New-Item -ItemType Directory -Force "$dst\$n" | Out-Null
     Copy-Item "$s\ponytail\skills\$n\SKILL.md" "$dst\$n\SKILL.md" -Force
   }
   ```

   Use `skills/<n>/SKILL.md`, **not** `.openclaw/skills/<n>/SKILL.md`: the two copies
   differ, and `skills/` is the source of truth (`skills/plugin.json` points at it).

5. **Required before these five are usable.** Fix the folded descriptions, or the index
   and Settings will show `>` for each. Either change the parser once (recommended, see
   step 6 of Route 2) or, for this route only, inline the description in each copied file —
   join the indented continuation lines onto the `description:` line in `ponytail-review`,
   `-audit`, `-debt`, `-gain`, `-help`. If you inline, note in `UPSTREAM` or a comment that
   these five are no longer verbatim, because the repo's stated policy is that vendored
   files are kept verbatim (see the Skills section of the README, and the module comment
   at `skills.rs:2-6`).

6. Nothing else is required to *load* them: no manifest, no registry, no restart of the
   app. `Skills::load` runs when a harness is constructed (`harness.rs:425`), so **start a
   new session/agent** for the system-prompt index to include them; Settings → Agent skills
   re-reads immediately (`skills_catalog`, `main.rs:856`) and will list each with origin
   "Yours" or "This project".

7. Optional — inject rather than merely offer. In `backspace.toml`:
   `[workflow] main_skills = [...]`, `worker_skills = [...]`, `triage_skills = [...]`
   (defaults at `config.rs:145-147`). Every agent can load any skill with the `skill` tool
   whether or not it is injected (`docs/SKILLS.md:41-44`), so injection is only for what a
   role should always have in mind — for 20 new skills, prefer leaving them uninjected.

8. Verify: Settings → Agent skills should list 27 skills (7 existing + 20), each with a
   real description — any row showing `>` means step 5 was skipped. Then in a new session
   let one agent run `skill` with `animate` and `file` = `RECIPES.md` to confirm satellite
   loading.

#### Route 2 — vendored (ships in the binary; needs `DEFAULTS` + a rebuild)

1. Copy each chosen skill folder into the crate:
   `crates/core/skills/<name>/SKILL.md` (plus its satellite `.md` files). Example targets:
   `crates/core/skills/animate/{SKILL.md,RECIPES.md}`,
   `crates/core/skills/review-animations/{SKILL.md,STANDARDS.md}`,
   `crates/core/skills/ponytail-review/SKILL.md`.
2. Register it in `DEFAULTS` (`crates/core/src/skills.rs:25-33`), listing **every** file —
   the `vendored!` macro only embeds what is named, so an omitted `RECIPES.md` would be
   silently missing rather than an error:

   ```rust
   const DEFAULTS: &[(&str, Files)] = vendored! {
       // …existing…
       "ponytail-review" => ["SKILL.md"],
       "ponytail-audit"  => ["SKILL.md"],
       "ponytail-debt"   => ["SKILL.md"],
       "ponytail-gain"   => ["SKILL.md"],
       "ponytail-help"   => ["SKILL.md"],
       "animate"         => ["SKILL.md", "RECIPES.md"],
       "review-animations" => ["SKILL.md", "STANDARDS.md"],
   ```

   `defaults_load_with_descriptions` (`skills.rs:229`) to assert each default's description

   suite stays green while the UI shows `>`.
4. Add `crates/core/skills/LICENSE-emilkowalski-skills` (copy of the repo's 1070-byte MIT

#### Which route to pick

Route 1 for evaluation, Route 2 for anything that should be present on every install.
If the plan is to ship a *catalog* the user picks from, neither route is the intended one:
`docs/SKILLS.md:71-74` sketches a repo-side skills *library* ("read it the way `Apps` reads
its catalog, and copy a chosen one into the user's folder") that does not exist yet, and
today Settings can only open the user folder and copy a template
(`main.rs:892-915`). One further caveat for Route 1: `npx skills add …` writes into other
harnesses' folders, not Backspace's, so the copy steps above are the mechanism.

### Work that is optional but worth doing regardless

The `>` description bug predates this research and affects `ponytail` today, in the
Settings list and in every agent's system prompt. Fixing the parser (Route 2 step 3) is
independent of whether any of these 20 skills are ever installed.
